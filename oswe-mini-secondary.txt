## Transfer lifecycle (init → in-progress → success/failure)
Flow used and enforced by the new code:
1. INITIATED
   - API accepts request and creates a transaction with a unique tx_id (UUID).
   - Audit log: initiated event.
2. POST DEBIT
   - Orchestrator posts debit with retry/backoff.
   - On success: state → DEBIT_POSTED and event logged.
   - On non-retryable failure: state → FAILED; attempt rollback/compensation.
3. POST CREDIT
   - After successful debit, post credit with retry/backoff.
   - On success: state → CREDIT_POSTED.
   - On failure: state → FAILED; deterministic attempt to rollback the previous debit.
4. COMPLETED
   - When both debit and credit confirmed, set state → COMPLETED.
   - Only after this is a success returned to the user.

Where "false success" could occur on previous system:
- API returned success immediately after enqueueing or after partial steps (eg. after debit posted or queue accepted), without verifying ledger confirmation.
- Missing compensation and rollback when credit failed after debit was applied.

---

## Root causes (concrete)
- Async posting failures were not propagated back to API (callbacks silently dropped or not awaited).
- State machine gaps — lacked a required state to ensure both legs completed prior to success.
- Missing rollback/compensation for partial success (debit succeeded, credit failed).
- Insufficient structured auditing: transaction IDs and state transitions were not consistently present in logs, preventing quick reconciliation.

Evidence: captured in root_cause_analysis.md and simulated by the `mocks/mock_ledger_service` events included in test traces.

---

## Recommended backend changes
1. Strict state-machine persisted for transactions (INITIATED → DEBIT_POSTED → CREDIT_POSTED → COMPLETED / FAILED).
2. Only return "success" if final state is COMPLETED. Otherwise return IN_PROGRESS or FAILED with actionable reason.
3. Add strong retry policy for transient (retry) responses with exponential backoff.
4. Implement deterministic compensation: if debit succeeded and credit ultimately fails, run rollback and set state FAILED with audit events.
5. Emit structured audit logs for each state transition and key ledger attempts — include tx_id (UUID), masked account references only.
6. Operational reconciler: background job that finds in-doubt transactions and attempts reconciliation or raises alerts.
7. Add idempotency keys for ledger posts — prevents double-debits on retries.

## Tests (5 repeatable integration scenarios)
All cases are defined in transfer_cases.yaml, and run by run_suite.py:

1. normal_success — debit OK; credit OK => final state: completed
2. debit_failure — debit is permanently rejected => final state: failed (debit-related)
3. transient_debit_then_success — debit returns transient (retry) then succeeds => final state: completed
4. credit_failure_requires_rollback — debit ok; credit fail => final state: failed & rollback attempted
5. credit_timeout_then_retry_audit — credit times out => final state: failed; audit should include tx_id

Each scenario uses the mock ledger to deterministically simulate each case.

## Structured logging / audit
- Schema: audit_schema.json (JSON Schema)
- Key fields include:
  - ts (timestamp), tx_id (UUID), event (initiated / debit_attempt / credit_attempt / rollback etc.), state, account_ref (masked/minimal), amount, result, error, retry_attempt.
- Logs should always include tx_id for reconciliation; do not log full PII (masking required).

Example audit line:
{ "ts":"2025-11-26T12:34:56Z", "tx_id":"abcd-1234", "event":"debit_attempt", "state":"debit_posted", "result":"ok", "retry_attempt":1 }
