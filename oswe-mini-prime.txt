Mapping of the transfer lifecycle (init -> in-progress -> success/failure)
- INIT
  - A transaction record is created with a unique `tx_id`.
  - Log: transfer.initiated (includes tx_id/from/to/amount)
- IN_PROGRESS
  - Debit request posted to the ledger. If committed, recorded; else retry, or failure -> mark transaction FAILED.
  - Key motions: `ledger.debit(...)` -> log `transfer.debit_committed` on success.
- CREDIT
  - Credit request posted to the ledger. If committed, mark transaction SUCCESS; if transient failures, retry via configured attempts; if permanent failure or retries exhausted, invoke rollback.
  - Key motions: `ledger.credit(...)` -> log `transfer.credit_committed` on success.
- ROLLBACK
  - If credit fails after the debit, the rollback reverses any committed ops and sets transaction to FAILED.
  - Rollback logged via `ledger.rollback` and `transfer.credit_unresolved_rollback` events.

Where pending operations can silently fail
- UI or API prematurely report success when only the debit occurred and the credit was never completed or was pending.
- Node or network connectivity that causes `transaction` to be persisted in memory only, not durable DB, leading to state lost on process restart.
- Missing rollbacks on credit failure or inability to persist the rollback result.
- No idempotency that causes retried operations to be accepted or applied multiple times.

Concrete root causes identified
- Async posting failures: We found that partial commits occur when only debit commit is recorded and the credit call either times out or fails.
- State-machine gaps: Without enforcing final ledger confirmation for both debit and credit, the system can mark a transfer as SUCCESS prematurely.
- Rollback omissions: When ledger confirms debit but fails credit, the system may not run a rollback or the rollback may not complete (evidence: ledger tx state shows debit committed but not credit; no `rolled_back` entry).
Evidence and logs
- All key events log with `tx_id` in JSON format so reconcilers can find and reconcile partial transactions without exposing sensitive data.
- Example logs in example_audit_lines.log and schema audit_schema.json.

Remediation recommendations (from remediation_plan.md)
- Ensure final state is derived from idempotent ledger confirmations, not in-memory assumptions.
- Implement idempotency keys across debit/credit calls using `tx_id`.
- Add retries with configurable counts & backoff on transient errors; after exhausting retries, invoke rollbacks and mark transaction as FAILED.
- Add audit logs and reconciliation to detect inconsistencies; run periodic repair jobs for partial commits.
- Add monitoring and alerts for partial commit patterns (e.g., debit commit without credit commit after threshold time).

Integration tests (five)
- normal_success — a straight-forward success scenario.
- posting_credit_permanent_failure — credit fails permanently; ensure rollback and final ledger unchanged.
- transient_retry_then_success — credit transient failure then success (behaviors list), ensure retries work and final ledger correct.
- timeout_retry_and_rollback — all retry attempts for credit are transient failures and revert to rollback; ledger unchanged.
- audit_verification_success_committed — success path verifying presence of `transfer.debit_committed` and `transfer.credit_committed` in logs.

Structured logging and transaction IDs

## 🐞 Troubleshooting & common issues
- If the script shows no output or fails:
  - Ensure the venv python path is correct: python.exe
  - Make sure requirements.txt is installed.
- On Windows, run_tests.sh (bash script) requires bash/Git Bash/WSL; instead use `run_transfer_suite.ps1`.
- If imports fail:
  - Confirm `sys.path` includes the project root in the runner. The scripts add it automatically; if you run test code manually, add `sys.path.insert(0, os.path.abspath('.'))`.
- For failing tests:
  - Inspect the captured logs and the `final_state` returned in run_suite.py.
  - Look for logs:
    - `transfer.debit_committed` and `transfer.credit_committed` (success)
    - `transfer.credit_transient_failure`, `transfer.credit_failure`, `ledger.rollback` (error or rollback)
- For flaky behaviour:
  - Increase `retry_delay` in `TransferManager` to observe retries.
  - Validate `behaviors` array in YAML: a list like `[transient_failure, success]` forces a transient failure followed by success on retry.

---

## 🧾 How to interpret a failure / False successes
- If a case logs `transfer.initiated` and `ledger.debit` but you never see `transfer.credit_committed`:
  - The credit may have failed uncommitted; check `ledger.rollback` or the transaction final state via the API helper (`get_transfer_status`).
- Confirm balances via `mock_ledger_service.get_balance` to ensure rollback or correct commit occurred.
